## Payment and cancellation decision

The user first suggests charging on completion if uncomplicated. Native inspection establishes that CraftComponent.CraftReally removes needs_from_wgo before setting is_crafting. Native FinishCurrentCraft -> ProcessFinishedCraft -> GameSave.OnFinishedCraft owns completion and the accepted formula reward; it does not defer that resource payment. A delayed-payment variant would need to prevent unpaid rewards and decide what happens if science is absent at completion.

The user explicitly chooses native upfront science reservation with full return on cancellation. 0.1.42 keeps science in native needs_from_wgo for UI/resource checks and payment, removes faith needs, and stores only the prepaid amount in table.data's namespaced rar_research_reserved_science parameter after a successful active source-job start. This is fee metadata, not another science currency balance. Stable job IDs and native serialized progress remain. Native SerializableWGO.item owns the table Item; native ToWGO restores the saved item and DeserializeCraftComponent restores the native work. Completion consumes the already-paid fee without a second charge and clears its metadata after native End. A successful native Cancel clears work first, then our scoped postfix returns exactly the prepaid fee to that same table and clears metadata. Used work/energy is not refunded. Cancellation of a legacy handed source job without fee metadata returns its original diagnostic one science rather than the new catalog fee; already paid faith stays in native consumed-items refund handling.

Static owner evidence: CraftComponent.Cancel drops _cur_craft_items_used (inventory/sample/faith inputs) and calls End, but never returns needs_from_wgo. Native Cancel callers include CraftGUI.NeedToCancelCraftsDialog's callback and CraftQueueGUI.OnDeleteItemPressed. This does not establish that every study UI exposes a convenient cancellation button. Candidate-only F9 calls the actual native Cancel for exactly one active study-table job (ordinary Survey or our research), with GUI closed; zero or multiple active study tables produce a no-op log. It does not fabricate progress/reward/refund or add a production UI commitment.
